# 三种语言的 Kubernetes 文档

Kubernetes 文档中的五个页面，每个页面都有英文原文和官方的中文、日文译本，用来衡量跨语言的抽取和治理。知识不依赖于书写它的语言，所以一个页面和它的译本应当让每个事实只有一个值，并算作一个来源。这些译本并非都是最新的：其中三个日文页面比英文原文早两到三年。英文版见 [README.md](README.md)；两者不一致时以英文版为准。

```bash
pnpm bench ingest examples/kubernetes-docs   # 内存中运行，约 3 秒
pnpm bench ask examples/kubernetes-docs "How many nodes can a Kubernetes cluster have at most?"
```

在常规报告之后，对照检查（与 [examples/control](../control/README.zh.md) 相同）把每个页面标为 **right**（正确）、**known gap**（已知差距：与 `expected.yaml` 记录的方式一致地不同）或 **differs**（不同），问题检查对 `questions.yaml` 中的每个问题也这样标注。`apps/bench/test/kubernetes.test.ts` 在内存和 Postgres 上运行这两项检查。`ask` 以语料的读者身份回答一个问题，并给出引用和说明。

## 运行结果

使用替身模型时，4 个有事实的页面中 1 个正确，其余 3 个是已知差距，全部来自替身模型：

- **陈述：** 答案预期的 33 条中有 29 条以正确的值落在正确的槽位，另有 18 条落进了不该进的槽位或带着不该有的值。
- **来源：** 11 个值中有 9 个的来源符合预期：跨三种语言，每个值一个来源。
- **提议：** 11 个槽位中有 10 个的提议值符合预期。

引擎负责的部分全部正确：

- **一个页面和它的译本是一个来源。** 每个以多种语言读出的值都只算一次，无论是三种语言中的哪几种写明了它。
- **原文优先于译本。** 有七个值只有译本写明，而且每个译本的原文写的是另一个值，它们无需人工即被处理：都是替身模型对日文和中文页面的误读（"Kubernetes v1.37 では" 中的 1.37，一串延迟中的 10、20、40 秒）。同一条规则也处理落后的译本：测试把英文页面的节点上限改为 6,000，于是 6,000 成立，只有译本仍写着的 5,000 无需人工即被处理，保鲜为两个译本各发出一条复核。
- **旧译本与原文一致。** 2023 年和 2024 年的日文页面对所跟踪的每个事实都给出相同的值。它们缺少此后新增的章节，而不是写着旧的值。

真实页面暴露了两个解析缺陷，现已修复。HTML 源码中的换行把一句话断开了，所以英文和中文页面中的 10 分钟重置没有读出。省略号后接逗号（"(10s, 20s, 40s, …), that is capped at 300 seconds"）被当成句末，所以英文的 300 秒没有读出。

替身模型的错误（预期真实模型不会犯）：

- **过于宽泛的别名：** "nodes" 匹配任何提到节点的段落，所以 "memory.available<100Mi (Linux nodes)" 把 100 放进了节点上限。
- **用单词写的数字：** "up to three minor versions older" 里没有数字，所以 kubelet 的版本偏差改从 "1.25" 中读取。
- **另一种单位：** 日文页面把重启延迟上限写作 "5分"（5 分钟），替身模型只读秒，而真实模型会给出目录中的单位。
- **一个词指所有宽限期：** 日文的 "猶予期間" 也指硬驱逐的 0 秒和 preStop 回调额外获得的 2 秒。

`expected.yaml` 完整给出了每个原因。真实文本还带来一个发现：中文的驱逐页面漏掉了 Windows 节点内存默认值那一行，并把 "（Windows 节点）" 加到了下一行上，所以读取它的模型会把节点文件系统阈值只归到 Windows 下。这里还没有跟踪这个限定条件。

## 问题

这些问题用英文、中文和日文询问所跟踪的事实，另加一个这里没有答案的问题。回答包含一个预期文本、并引用了某个预期页面（任何语言的版本均可）时，算作正确。在模型替身下（回答由与问题共享词语最多的来源句子组成，重排器只数共享的词），12 个问题中有 9 个正确。检查还会说明回答所依据的搜索是否找到了预期文本：11 个有答案的问题全都找到了，所以错误出在替身的回答上，而不是搜索上。回答读到的每段原文都是整段，所以列表引导句下面的列表项也能交给它。

每个问题还会交给两个对手，用同样的文档和同样的替身模型：一个是在同样的文本块和检索上做的成熟 RAG，没有陈述也没有治理；另一个是一次读完全部 15 个页面（按引擎的估算约 77,000 个 token）的模型；还会交给治理之后读完全部 15 个页面的引擎。三者都答对 12 个中的 8 个。在彼此一致的页面上，知识层本就不应该胜出；它应当在事实发生变化时胜出，如下所示。

引擎始终做对的部分：

- **无论哪种语言，都给出现行值。** 英文页面把节点上限提高到 6,000 之后，用中文提问得到的是英文的 6,000，并附一条说明，指出中文页面仍写着 5,000。写着 5,000 的那句中文不会交给回答；交给回答的是它的陈述，标为已被取代，并附上现行值的陈述。对同样文本块的成熟 RAG 仍然回答 5,000：它的替身不会像被告知要看日期的模型那样比较页面的日期。
- **说明只针对回答给出的值。** 冲突说明跟着节点上限出现（替身抽取给它读出了七个值），不会出现在关于阈值的回答中。
- **没有答案的问题是一个缺口。** 护照问题什么也不引用，并如实说明。

错误都记录在 `questions.yaml` 中，并附原因：

- **同一件事的不同说法：** "at most" 与 "no more than"，以及日文的 上限 与 最大。
- **假名与汉字：** 日文问题写的是 しきい値，页面写的是 閾値。

配置好真实模型后，应当再用同一份语料运行一次。届时替身模型的错误衡量的就是抽取质量，而引擎负责的部分应当保持不变。
