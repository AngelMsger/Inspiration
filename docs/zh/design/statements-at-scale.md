# 规模化的陈述：结构与复核负担

状态：已采纳的设计，2026-10-24。文中的实测数字来自模拟原型，对应拉取请求 #8、#9 和 #10，这三个 PR 已于 2026-10-26 合入。配套文档：[界面原则](ui-principles.md)。本文是英文版 [docs/design/statements-at-scale.md](../../design/statements-at-scale.md) 的中文副本，两者不一致时以英文版为准。

## 问题

引擎把来源转换成陈述。一条陈述就是一个事实，带着它的状态、维护人、生效日期，以及它所依据的段落。抽取会产生大量陈述：在一个有 10,000 份文档的合成企业里，对每个来源的每个段落都做抽取，会得到约 137,800 条陈述。如果每个空间只是一张平铺列表，这样的数量既无法浏览也无法维护；如果每条陈述都有自己的复核，负责保持知识最新的人会被工作淹没。

设计分三部分：

1. **每条陈述在两份大纲里都有位置**，关于同一事实的陈述共用一个**事实槽**。
2. **不是每个来源都要治理。** 每个来源或文件夹有一个治理级别。
3. **人复核的是分组，不是单条陈述。** 工作按维护人、主题和周分组，并受每周预算限制。

三者合起来，让维护人的工作量随主题数和来源变更增长，而不是随陈述数增长。

## 术语

| 术语 | 含义 | 契约中的名称 |
| --- | --- | --- |
| 企业 | 一家公司的共享区域，例如恒远机械 | Tenant |
| 空间 | 企业中的一个区域，如财务部或采购部。由它的维护人决定谁能阅读 | Space |
| 成员 | 企业里的一个人 | Principal |
| 来源 | 在原应用中按原样保存的文档：飞书知识库页面、表格、上传的文件 | Source, SourceRef |
| 段落 | 引擎从来源中切出的片段。之后的每一层都指回段落 | Span |
| 陈述 | 最小的受治理单元：一个事实，带状态、维护人、生效日期和段落 | Claim |
| 主题 | 空间知识大纲中的节点，最多三层（领域、主题、子主题） | TaxonomyNode |
| 知识页、流程、卡片 | 读者看到的形态，由陈述写成；卡片描述一个对象，例如城市、供应商或角色 | PageSpec, Sop |
| 主题维护人 | 维护一个主题的陈述的成员：确认它们的归属、复核它们、裁决冲突。界面上从不单说“维护人” | TaxonomyNode.owner_id |
| 空间维护人 | 整个空间的维护人，接手没有维护人的主题 | 空间角色 `owner` |
| 待办 | 给某个人的一项工作，显示在待办箱的卡片上 | Todo |

## 第一部分：两份大纲与事实槽

一条陈述总是同时位于两份大纲中，人们通过其中一份来浏览它，而不是看一张平铺列表。

- **来源大纲：它从哪里来。** 来源、文档、章节、段落。陈述继承它所引用段落的章节。这不需要模型调用：规范化后的来源中，每个块都带有标题路径，而且块 ID 在不同版本之间保持稳定。一篇长论文显示为它自己的目录，陈述折叠在各章节下面。
- **知识大纲：它在哪里被使用。** 空间、主题、页面、页面小节、句子。一条归属记录（`Placement`）保存陈述所在的主题，以及在有页面引用它时对应的页面块。归属可以由聚类、由引用该陈述的页面或由成员建立。维护人确认之后，重新聚类不会再移动它。
- **事实槽：它说的是什么。** 槽键（`Claim.slot_key`：主语、谓词和限定条件，经过规范化）相同的陈述说的是同一个事实。一个事实槽保存来自不同来源的每个变体和随时间变化的每个版本，所以来自三份文档、四个版本的十条陈述只是一行需要维护的内容，冲突也发生在一个事实槽内部。数字、日期、限额和指定维护人很适合放进事实槽。自由文本的规则往往不适合，它们继续按页面小节分组。

演示语料中的例子：事实槽“深圳 · 每晚住宿上限 · 经理及以下”保存着差旅制度第 6 版中的 600 元（有争议）、价目表中的 650 元（有效）和制度第 5 版中的 550 元（已取代）。使用这个事实槽的知识页、流程和深圳卡片读取的都是同一个值。

主题来自聚类。由聚类产生的主题在维护人确认之前处于“提议”状态，读者永远看不到提议中的主题。主题键在重新聚类时保持稳定，且从不复用。来自严格级别文档、还没有主题的陈述属于**未归类**：它显示在来源章节下，附带一个建议主题和接近程度分数，直到维护人把它归档。

## 第二部分：治理级别

公司导入的大部分内容是参考资料。逐条治理这些内容正是数量的来源，所以治理级别（`GovernanceLevel`）按来源设置，文件夹在来源树中向下继承。

| 级别 | 典型来源 | 抽取什么 | 维护人、复核、冲突 | 读者看到什么 |
| --- | --- | --- | --- | --- |
| 严格（`governed`） | 制度、价目表、SOP、审批流程、正式规范 | 规则、事实、指标、定义、流程步骤 | 主题维护人、复核时钟、冲突待办 | 知识页、流程、卡片 |
| 宽松（`reference`） | 论文、文章、研究报告、会议纪要、供应商文档 | 只在使用时抽取：页面引用某个段落、回答用到它，或它触及一个已知事实槽 | 没有维护人，也没有复核。与严格级别的值不同的值只给那位维护人发一条备注，从不产生冲突待办 | 原文和批注视图；回答中的引用标为宽松级别 |
| 仅检索（`search_only`） | 聊天记录、草稿、个人笔记、大型归档 | 不抽取。段落只建索引，用于检索和回答 | 无 | 来源树和搜索 |

- **默认值。** 上传文件和网页一开始是宽松级别。超级管理员在接入每个来源（例如一个飞书知识库空间）时选定它的级别。空间维护人可以在来源树中修改任意文件夹的级别。
- **提升只需一个操作。** 当维护人把一条宽松级别的陈述采纳进页面时，它就变成严格级别，并获得一个事实槽和维护人。
- **陈述类型也有影响。** 观点、结论、假设和计划即使在严格级别的来源里，也不会单独产生复核待办。它们跟随使用它们的页面。
- **宽松级别的文档照样好读。** 它的原文视图、大纲和带引用的回答，不需要任何一条严格级别的陈述就能工作。

## 第三部分：分组复核

人看到的工作，单位是他们自己思考时用的单位：一份改了的文档、一个到期的主题、一个有争议的值。绝不是每条陈述一行。

- **交给谁。** 待办交给其陈述所在主题的维护人，没有时交给主题树中往上最近的维护人。没有维护人的主题交给空间维护人。
- **每位维护人、每个主题、每周一张卡片。** 同一维护人、同一主题、同一个 ISO 周的待办共用一张待办卡片（`Todo.batch_key`，配合 `taxonomy_key`、`slot_key` 和 `week`）。一张卡片最多 20 条待办，先按优先级、再按时间排序，冲突排在依赖它的复核之前。
- **每周预算。** 每位维护人每周最多 10 张卡片。一周满了之后，多出的卡片顺延到之后的周；高优先级和紧急的工作从不顺延。
- **来源自己改了值，不打扰任何人。** 措辞变化、条款重新编号、同一来源里的值变化都直接同步，旧值留在历史里。只有人更正过或裁决过这个值、或几个来源说法不同时才问人。
- **副本随冲突一起处理。** 重复某个争议值的文档在该事实槽的冲突待办里一起复核（“用在 5 处，决定后一起更新”），而不是作为单独事项。
- **备注不占预算。** 当只有宽松级别的文档给出不同的值时，维护人在每周备注卡片上收到一条备注（`TodoKind` 中的 `note`）。备注不需要做决定，一个操作即可确认；标题和详情写明该文档、它的日期、事实槽和两个值。
- **工作会自行撤回。** 冲突或备注的原因消失时（例如宽松级别的文档被更正），它会自动撤回，不需要任何人操作。
- **第一天是一次专项清理。** 企业第一次接入来源时就已到期的复核，进入按空间和主题划分的首次复核专项卡片，每张最多 20 条，由空间维护人在紧凑模式下处理。维护人的待办箱从正常的每周节奏开始。

读者看到的刻意很少。有效和正在变旧的知识不显示任何东西。过时和有风险的陈述只在引用浮窗和追溯视图里显示“待复核”。正文中唯一的行内标记是“已过时”和“有争议”。

## 维护人看到什么

- **待办箱**每周只有几张卡片：每个到期主题一张复核卡片、带副本复核的冲突卡片、备注卡片，以及给空间维护人的专项卡片。
- **追溯视图中的主题总览**按一个主题约 1,000 条陈述设计，而且从不逐条列出：先是事实槽，每个一行并带上各个变体和状态；然后是使用它们的知识页、流程和卡片；然后是其余所有内容，按来源文档折叠，只显示计数；最后是带建议主题的未归类陈述。引擎用一次读取提供这些内容。
- **页面级的追溯视图**按页面小节对页面的陈述分组，因为一个页面只引用 5 到 30 条陈述。

## 原型实测

测试环境是一个有 10,000 份文档的合成企业：严格 1,366 份（14%），宽松 5,530 份，仅检索 3,104 份。模型是确定性的模拟，向量是假的，所以这些数字衡量的是数量，不是质量。

**导入。** 同步用时 71 秒，规范化 240 秒，产出 161,000 个块和 205,000 个段落。典型文档有 16 个块（p90 为 22）。块 ID 在不同版本之间保持稳定，每个新版本都附带差异。同一制度的不同版本相似度在 0.83 到 0.93 之间，足以把各版本串成一个事实槽的历史。

**抽取与治理**（拉取请求 #8）：

| 指标 | 数值 |
| --- | --- |
| 抽取的陈述 | 39,900（如果所有来源都是严格级别则为 137,800） |
| 合并重复后 | 17,500 |
| 位于事实槽中的陈述 | 59% |
| 模型调用 | 5,635（如果所有来源都是严格级别则为 10,001） |
| 带复核时钟的文档 | 1,283 |
| 每周到期的复核，中位数 / 最多 | 11 / 91 |
| 冲突待办 | 30（28 条普通，2 条高优先级） |

宽松级别的文档每份中位数产生 1 条陈述，只在触及已知事实槽的地方。宽松级别的段落第一次被引用时约增加 1 条陈述。在模拟中这需要 13 毫秒，真实模型会更久，所以引用浮窗立刻显示段落，从不等待抽取。

**主题**（拉取请求 #9）：41 个主题，最多三层。每个主题的陈述数：中位数 1,143，p90 为 2,375，最多 6,206。每个主题的不同陈述数（一个事实槽算一次）：中位数 540。每个主题的事实槽数：中位数 1，最多 30。第二次运行或一轮编辑后，没有任何陈述改变主题（25,660 条中为 0）。在手写的演示语料上，20% 的严格级别陈述仍未归类，全部来自三份小文档。

**分组复核**（拉取请求 #10），模拟一年，15 位维护人：

| 指标 | 数值 |
| --- | --- |
| 复核卡片 | 606 |
| 每位维护人每周卡片数，中位数 / 最多 | 1 / 4 |
| 每位维护人每周待办数，中位数 / p90 / 最多 | 2 / 5 / 26 |
| 第一天的复核 | 605 条，分在 44 张专项卡片上 |

每周预算从未需要顺延任何卡片。最多的 26 条待办出现在第一周，那时 30 个冲突同时到来，所以一位维护人的第一周可能有同一主题的两张满卡片。在 10,000 份文档时没有备注留下，因为严格级别的指南之后都给出了宽松级别文档提到的每个值；演示语料保留了一条。

## 决定

均于 2026-10-24 采纳：

- 上述三部分：带事实槽的两份大纲、治理级别、分组复核。
- 上传文件和网页一开始是宽松级别；每个接入来源的级别由超级管理员选择。
- 每周预算为每位维护人 10 张卡片，每张最多 20 条待办，之后根据数量报告调整。
- 宽松级别的来源从不阻塞严格级别的陈述，只产生一条不占预算的备注。
- 本设计建立在知识视图之上：来源的原文、批注和知识三个视图，以及来源树和知识树。

## 仍待解决

- **主题拆分需要真实向量。** 合成企业在许多部门指南中反复表述同样的 30 个对象，假向量分不开这些章节，所以主题随语料增长而变大，而不是拆分。只有用真实向量才能评判自动拆分。
- **按使用和风险排序。** 设计按陈述的使用程度（被知识页、流程或卡片引用，或最近在回答中被用到）、风险类别（价格、制度）和抽取置信度对待办排序。原型目前按优先级和时间排序。
- **真实维护人的负担。** 合成数据中的维护人是随机分配的，每位维护人的负担需要真实企业来确认。
- **跨语言的事实槽。** 中文制度和日文纪要里说的同一个事实应当共用一个事实槽。目前槽键中的限定条件保留来源原文的用词，所以规范化需要做到与语言无关。见[界面原则](ui-principles.md)中的“国际化”一节。
