# MVP：一个能用、跑通业务闭环的产品

状态：提议中，2026-11-04。依据产品负责人 2026-11-04 的决定：接受验证的结果，把 10 个百分点的目标留到以后，下一步做一个能用的原型（[验证知识核心](validation.md#现在的状况)）。它把[业务层](business-layer.md)的第一阶段和引擎余下的阶段（[概览](../overview.md#24-下一步与工作量)）收窄为一家企业的完整闭环。本文是英文版 [docs/design/mvp.md](../../design/mvp.md) 的中文副本，两者不一致时以英文版为准。

## 结论

- **MVP 是一家企业的完整闭环，用真实的登录和企业自己的文档。** 一个人登录、创建企业、邀请同事。文档上传到空间里。任何人用英文、中文或日文提问，得到带引用、又快又便宜的回答。负责人看到的待办很少，因为"替我决定"处理掉例行的复核和冲突。上传改过的文档，回答随之改变。智能体通过 MCP 读取同样的知识，权限与成员相同，不多一分。
- **现有证据实测了六项优势中的三项，估算了第四项；另外两项由 MVP 构建所需的修复。** 在我们的测试语料上实测：回答比成熟 RAG 更准，但所用语料也是设计治理修复时用的那一份；不需要旗舰模型，也不需要思考；回答的输入小得多、便宜得多。只是估算、没有实测：在读多写少的主题上，按现在每次回答省下的钱和给定的提问量、更新频率，阅读的模型费用能收回；这个数字不含人处理待办的时间。还没有证明：治理只占用人很少的时间（每 100 份文档 33 条待办，没有任何一条被代为处理）；整次回答很快（在我们只有 CPU 的机器上检索要 11 秒）。MVP 构建"替我决定"和更快的检索，再在真实使用中测量这两项（[MVP 必须证明什么](#mvp-必须证明什么)）。
- **约 16 人周，分六个切片，前三个完成后就有第一个可用版本**（[切片](#切片)）。不做：个人空间和发布、联合审批、邮件和聊天应用通知、实时同步飞书等来源连接、研究、视图、代码图谱和计费（[范围](#范围)）。
- **五个决定属于产品负责人：** 谁先试用、部署在哪里、是否包含飞书实时同步、试用的模型预算，以及负责人首次访问时是否提供长期的"替我决定"。每一项都有推荐的默认选择（[需要产品负责人决定的](#需要产品负责人决定的)）。

## MVP 必须证明什么

产品负责人 2026-11-04 的标准：定性方向必须对，数字可以暂时落后。领先不到 10 个百分点，或者期望降本 60% 而实测只有 40%，都可以接受；治理成本远超预期、回答省下的又远低于预期，则不行。证据来自[验证](validation.md#现在的状况)，模型为 `deepseek-flash`，关闭思考。

| 优势 | 现有证据 | MVP 做什么 | 试用中测量什么 |
| --- | --- | --- | --- |
| 回答比成熟 RAG 更准 | 治理修复后 276 题中 248 对 234（在设计这次修复所用的同一语料上实测）：+5.1 个百分点（95% 区间 +1.1 到 +9.4），在有变化或冲突的事实上 +6.9。精简回答 242 | 用受治理的知识回答，和测试时一样 | 用户报告的错误回答及原因；经同意后，留作更大数据集的案例 |
| 不需要旗舰模型，不需要思考 | 以上结果都用便宜模型、关闭思考得出；在每百万输入 token 0.10 美元的 GPT-6 Luna 上，Inspiration 和成熟 RAG 在共享盘测试集上打平（各 134） | 阅读和回答都用一个便宜模型，关闭思考 | 每个回答背后的模型和设置 |
| 输入更小，回答更便宜 | 每个回答：成熟 RAG 8,954 token、0.0083 元；Inspiration 5,024 token、0.0050 元（少 40%）；精简回答 1,961 token、0.0012 元（少 86%） | 默认用精简回答，需要时用标准回答 | 每个回答的模型费用，对比同一问题下成熟 RAG 的输入（离线计算，不调用模型） |
| 阅读的模型费用能收回 | **估算。** 每百万文档 token 约 6.6 元（实测）；按现在每次回答省下的钱，在共享盘测试集大小的主题上，约 260 个精简回答省下的钱就能收回，在决定性测试的两个主题上约 1,000 个。只算模型费用，不含人处理待办的时间和持续的变更 | 新上传的文档在用到时才读；文件夹被设为严格或常被问到后才完整阅读 | 每份文档、每家企业每月的阅读费用，对比该企业的回答省下的钱 |
| 治理只占用人很少的时间 | **没有证明。** 183 份文档 60 条待办，每 100 份 33 条，没有一条被处理，因为"替我决定"还没有构建；一次由人处理的提问，成本相当于约 1,260 个精简回答省下的钱（模型估算） | "替我决定"处理它能处理的，其余的带着理由留给人，每个决定都可以撤销 | 每 100 份文档产生的待办、被代为处理的和留给人的；每次提问占用的分钟数 |
| 整次回答很快 | **勉强。** 回答模型：精简回答 1.40 秒，成熟 RAG 1.73 秒；不含检索的整次回答 3.06 秒对 3.27 秒，长上下文 13.1 秒。在我们只有 CPU 的机器上，检索的中位耗时是 11.4 秒，其中 9.1 秒是重排 | 把重排移出 CPU，或用更浅的重排，用免费的仅检索检查来选 | 包括检索在内的整次回答耗时，中位数和 p90 |

## 流程

1. **登录并创建企业。** 第一个人是超级管理员。想先看看再上传的人，可以打开一家示例企业，即演示用的恒远机械语料。
2. **空间和负责人。** 超级管理员创建空间并指定负责人；每位空间负责人自上而下设定谁能读。来源的权限不继承，按已有决定。
3. **邀请。** 同事通过链接以成员身份加入企业。
4. **上传。** 文件或整个文件夹放进一个空间：Markdown、纯文本、HTML 和 CSV 现在就支持，另加 Word、PowerPoint、Excel 和 PDF。文档树立即按文档本来的样子显示它们；阅读在后台进行，显示进度，受企业每日预算约束。新上传的文档从宽松开始，用到时才读；空间负责人把存放制度的文件夹设为严格，或在某个文件夹常被问到时接受系统的建议。
5. **提问。** 成员用三种语言中的任何一种提问，得到用精简来源写成、带引用的回答；点开引用就是它所依据的那一行。
6. **待办。** "替我决定"处理它能处理的，每一项都写明理由；负责人看到剩下的，以及已处理事项的抽样，任何一项都可以撤销。
7. **文档变了。** 上传新版本只重读变化的块。它改变的值按已经构建的规则生效，或者请负责人处理，下一次回答随之改变。
8. **智能体。** 成员在"使用知识的应用"下创建令牌。MCP 客户端以这位成员的权限检索、提问和阅读；它自己只读不写。
9. **用量。** 超级管理员按成员和空间看到回答数、模型费用、回答耗时和每 100 份文档的待办，从不看到内容。

## 范围

**包含：** 用 Logto 登录，企业、成员、空间及其读者范围，三种产品角色；上传文件和文件夹，以及新版本；解析服务；用真实模型阅读，带预算；文档树、主题页和待办，与演示相同；"替我决定"；三种语言的带引用回答；通过 MCP 和个人令牌提供的智能体接口；一台已部署的服务器；用量和反馈。

**暂不包含：**

| 不做的 | 为什么可以等 |
| --- | --- |
| 个人空间和发布 | 试用在共享空间里进行，读者范围自上而下设定。两个领域的规则仍是设计；个人空间随试点一起做 |
| 联合审批、截止时间和兜底决定人 | 小团队每条待办一个决定人就够了 |
| 邮件和聊天应用通知 | 网页应用里的待办数量就够了 |
| 飞书等实时来源连接，凭证代理 | 文档改了就重新上传；见决定 3 |
| 单点登录、SCIM、通讯录同步、验证域名 | 通过链接邀请 |
| 智能体的 OAuth | 用个人令牌；等第三方客户端需要时再做 OAuth |
| 研究、视图和沙箱、代码图谱、追溯视图、个人知识库 | 不在要验证的闭环里 |
| 计费、套餐和席位 | 试用的预算手动设定 |
| 手机布局 | 先做桌面，和演示一样 |
| 验证运行 | 暂停，直到产品负责人重新开启这条线（[验证](validation.md#现在的状况)） |

## 切片

每个切片照常通过拉取请求合入。估算与[概览](../overview.md#24-下一步与工作量)的口径一致；引擎的最初几个阶段由智能体在几天内完成，所以日历时间更多取决于审查和集成，而不是这些数字。

| 切片 | 构建什么 | 人周 |
| --- | --- | --- |
| 1. 身份和企业 | 引擎：验证业务层签发的主体令牌，开通租户、成员和空间，访问控制改用空间读者范围、不再用来源 ACL（两个领域规则中的租户领域）。业务层：基于 Logto 的账号（邮箱和密码，通过链接邀请），带三种角色的租户，以及空间、负责人和读者范围的管理。网页应用：登录、成员和空间，浏览器只通过业务后端访问引擎 | 5 |
| 2. 文档进来 | 把文件、文件夹及新版本上传到空间；Word、PowerPoint、Excel 和 PDF 的解析服务，接在规范化的解析器契约后面；用真实模型阅读，带企业每日预算和进度；示例企业 | 3 |
| 3. 快速的带引用回答 | 默认用精简回答；把重排移出 CPU 或用更浅的重排；检索中稳定的并列排序，同一个问题每次拿到同样的来源；在回答读取的内容里标记有争议的值，让它说明来源不一致；记录每个回答的费用和耗时 | 1.5 |
| **关口 A，第一个可用版本** | 登录、创建企业、上传自己的文件、用三种语言中的任何一种提问、得到带引用的回答；打开示例企业 | |
| 4. 少打扰人的治理 | 待办分组和每张卡片上的"替我决定"，带理由，可撤销；按需阅读（文件夹设为严格或常被问到后才完整阅读） | 2.5 |
| 5. 智能体 | 智能体接口：带检索、提问和阅读的 MCP 服务，以成员身份行事；"使用知识的应用"下的个人令牌，可以吊销 | 2 |
| **关口 B，闭环跑通** | 通过链接邀请的同事只能读允许自己读的空间；负责人的待办显示"替我决定"留下的事项，带理由，可撤销；新版本改变回答；MCP 客户端只看到它的成员能读的内容 | |
| 6. 试用 | 服务器、沿用 `infra/` 的 Docker Compose、TLS、备份和日志；用量页和反馈按钮；各关口的脚本 | 2 |
| **关口 C，试用** | 团队以外的三到五个人用自己的文档试用两周；用量页报告上面列出的测量 | |
| **合计** | | **约 16** |

每个关口都是一个脚本，像业务层的集成关口一样，对真实的引擎和业务层端到端地跑一遍流程，在服务栈允许的地方放进 CI。谁做什么由协调者分配；自然的分工是：引擎线程做每个切片的引擎部分，演示线程做从演示发展而来的网页应用，一个业务线程做账号、租户和管理。

## 需要产品负责人决定的

1. **谁先试用，用哪种语言。** 推荐：产品负责人认识的一个团队里的三到五个人，用中文，用自己的非机密文档，试用两周。
2. **部署在哪里。** 推荐：香港或新加坡的一台云服务器，公开网站不需要 ICP 备案，也能访问 DeepSeek；约 8 个 vCPU、32 GB 内存，外加一块小 GPU 或托管的重排服务供检索使用；一个产品负责人自己的域名。中国大陆以后再做，届时办理备案。
3. **飞书实时同步。** 推荐：第一个版本不做，文档改了就重新上传。关口 B 之后再加飞书，约多 2 人周：凭证代理，以及基于现有飞书客户端的实时连接器。
4. **试用的模型预算。** 推荐：每月合计 100 元，每家企业有每日预算。一家有 500 份、每份约 3,000 token 文档的企业，阅读约需 10 元；按非高峰价格的两倍计，2,000 个精简回答约 5 元。DeepSeek 只获准处理内部级别的内容，所以机密文档不进入试用。
5. **长期的"替我决定"。** 推荐：负责人第一次打开待办时，提供"例行的复核和冲突总是替我决定"，默认选中，按一下即可接受，随时可以暂停。这是一个事先提出的请求，正是概览第 9 个开放问题所问的情况（[替我决定](decide-for-me.md)）；没有它，负责人要面对验证中测到的每 100 份文档 33 条待办。

## 风险

| 风险 | 缓解 |
| --- | --- |
| 治理占用人的时间仍然很多 | 默认"替我决定"，按需阅读，从第一天起在用量页上显示每 100 份文档的待办 |
| Office 文件和扫描件读不好 | 解析服务报告它读不了的部分；读取失败的文档保持仅检索，并注明 |
| 检索仍然慢 | 切片 3 在试用前用免费的仅检索检查选定重排方式 |
| 敏感内容被发给模型提供方 | 每次调用都带敏感级别标签，已经构建；试用的文档不是机密的 |
| 成员读到不该读的内容 | 切片 1 用空间读者范围取代来源 ACL，权限测试在两种后端上都跑；试点之前做红队测试集 |
| 范围不断扩大 | 只构建本计划列出的内容（AGENTS.md 的"Keeping the code simple"）；其余的都等产品负责人决定 |

## MVP 之后

与设计伙伴的[试点](../overview.md#8-版本范围与成功标准)、飞书实时同步、个人空间和发布，以及联合审批。等引擎形态稳定后，验证这条线在更大、更贴近真实使用的数据集上重新开始，把 10 个百分点作为引擎边界内的长期目标；试用中经同意保留的错误回答，可以作为这个数据集的开端。
