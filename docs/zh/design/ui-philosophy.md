# Inspiration 界面：设计哲学

状态：已采纳，2026-11-05；设计画布的第二版和 MVP 网页应用都按它来做。

## 结论

- **表面极简，底下完整。** 每个界面只给一个人手头这件事需要的东西，并按这件事的真实规模来画；其他东西都在一步之外，在面板、链接或 ⌘K 里。每个界面都要过三关：为谁、做哪一件事；按真实数量画出来是什么样；助手能在顶部说出什么，让人不用自己去读。
- **同一套语法，四个一眼分得出的地方。** 每个界面都有同样的顶栏、左栏、中间和右侧面板，但阅读、维护一个空间、管理后台和账户一眼就能分出来；每个界面都回答我在哪里、从哪里来、怎么去别处。越常用的东西放得越近。
- **配置跟着负责的人走：** 你自己、空间负责人，或者超级管理员。超级管理员决定谁和怎么做，从不决定知识说什么。
- **每个列表按真实规模来画：** 10 项以内全部显示，100 项以内分组或折叠，再多就先搜索或给出摘要。
- **助手安静地出现：** 每一堆东西之前先有概述，它的建议已经选好，“替我决定”放在整批上而不是每一项上，留给人的决定附一句理由，它做的每件事都有“为什么”和“撤销”。它没有头像、没有颜色，也没有聊天侧栏。
- **设计画布的第二版已经按这些规则绘制**（[界面](screens/README.md)）。还没定的：每个概述的卡片放哪几个数字，以及几个日文用词（[还没定](#还没定)）。

## 1. 立场：安静的表面，完整的纵深

极简还是全面？表面极简，底下完整。每个界面只显示一个人手上这件事需要的东西，并按这件事真实的规模来画。其余的都在一步之内：一个面板、一个链接或命令面板（⌘K），有人要时才出现在界面上。产品能做的事没有一件被永久藏起来，只是不挡路。

每个界面都要通过三个检验：

1. **它给谁用？这个人在这里的那一件事是什么？** 一个界面只有一个主要操作，其他操作放进菜单或 ⌘K。
2. **按真实的条目数，它长什么样？** 规模见第 6 节。真实有三百条、却只画三行的列表，是画错了。
3. **有哪些东西助手已经知道、而人本来得自己去读？** 放在最上面说出来，并让人按一下就能处理。

## 2. 五个信念

1. **人是来做自己的事的，不是来看我们的模型的。** 人熟悉的是文档、答案和决定。陈述、事实槽和来龙去脉是我们保证它们正确的手段。界面说前者的话；后者留在追溯视图里给负责人看。所以导入后先看文档，读者也从不看到知识的内部机制。
2. **阅读交给助手，决定属于人。** 助手读完所有内容，概括成堆的事，填好它的建议，在被要求时代为决定。每个决定仍属于一个具名的人，他能看到原因，也能撤销。
3. **注意力是我们处理的最稀缺的东西。** 让人读四十行才找到要紧的三行，这个界面就失败了。概述在列表之前，分组在条目之前，例外在常规之前。
4. **每样东西只有一个位置，就是负责它的人会去找的地方。** 导航跟着你所在的区域走，配置跟着负责的人走。一项配置只放在一个地方，别处链接过去。
5. **信任要展示，不靠声明。** 每样东西的原因、来源、谁定的、从何时起，都在一步之内。助手做过的任何事都能撤销。

## 3. 同一套语法，四个一眼分得出的地方

一致的是哲学，不是长相。产品负责人指出：每个界面都长得一样，人就不知道自己在哪；阅读一样东西和维护它，感觉不能一样。所以每个界面用同一套语法（顶栏、左侧栏、中间、右侧栏），但四个区域一眼就能分开，并且每个界面都回答三个问题：我在哪、我从哪来、怎么去别处。

| 区域 | 回答什么 | 放什么 | 从不放什么 |
| --- | --- | --- | --- |
| 顶栏 | 找任何东西。我是谁，在哪个企业？ | 用普通文字写的当前企业名、搜索与提问（⌘K）、账户菜单（也在这里切换企业、打开个人知识库） | 空间、页面标题、筛选，或这个界面自己的操作 |
| 左侧栏 | 我在哪个区域？这里有什么？ | 当前区域的导航，最上面一块写着区域名和回去的路 | 对选中条目的操作，或列表的筛选 |
| 中间 | 东西本身，以及它在哪 | 从区域开始的位置路径，然后是一份文档、一个页面、一个列表或一个决定 | |
| 右侧栏 | 选中的这一项怎么样？ | 写明选中了什么的标题，然后是适合这类东西的内容（见下文） | 导航 |
| 命令面板 | 按名字找到一切 | 每个地方和操作，带快捷键和 CLI 命令 | |

左侧栏显示四个区域之一，每个区域有自己的样子：

| 区域 | 给谁 | 从哪里进入 | 样子 | 左侧栏内容 |
| --- | --- | --- | --- | --- |
| 知识（默认） | 所有人 | 登录、首页 | 纸面底色，阅读时收起 | 首页、待办、我的空间，然后是这个人能读的每个空间，各自带文档和知识 |
| 维护一个空间 | 这个空间的负责人 | 空间上的“维护”，或待办里的卡片 | 淡蓝底的左侧栏，最上面是靛蓝色的一块：“维护空间 · 财务部”“← 回到阅读” | 概览、工作（复核、冲突、发布申请、批量变更）、主题与负责人、文档与治理级别、读者、规则、设置 |
| 管理后台 | 超级管理员 | 账户菜单 | 深色左侧栏，最上面写着“管理后台 · 企业名”“← 回到知识” | 按关注点分组，见第 5 节 |
| 账户 | 所有人 | 账户菜单 | 纸面底色，最上面写着“账户与设置”和“完成” | 你（资料与语言、登录方式、所在企业、通知），然后是当前企业（你的来源连接、使用知识的应用、总是替我决定、你的用量） |

阅读始终在纸面上，不带任何底色，所以一眼就分得出是在读还是在管。

### 我在哪、我从哪来、怎么去别处

- **我在哪。** 区域：左侧栏的颜色和最上面那一块。位置：中间最上面的位置路径，从区域开始，比如“维护空间 › 财务部 › 批量变更 › 第 4 版”。这一项：左侧栏的选中项和页面标题。
- **我从哪来。** 链接跨区域，或从页面跳到它的原文时，位置路径前面多一个回去的路，比如“← 回到《差旅报销标准》”。区域头里的“← 回到阅读”回到离开的地方。浏览器的后退永远有效，因为每个状态都有自己的地址。
- **怎么去别处。** 阅读和维护互相有入口：空间旁的“维护”，维护时检查器里的“去读这个领域”。⌘K 到任何地方，包括“切换到…”。账户菜单通往账户和管理后台。

### 右侧栏跟着选中的东西

规则处处一样：右侧栏永远有标题，写明它在说什么，并且只讲选中的那一项。里面放什么，由这类东西决定：

| 中间是什么 | 右侧栏的标题 | 右侧栏里有什么 |
| --- | --- | --- |
| 原始文档 | 选中的一段 | 评论、提一个修订、用到它的知识（V2-doc） |
| 知识页 | 本页 | 本页结构、这一页正在处理的事、相关页面、出处（V2-page） |
| 待办里的一个决定 | 关于这个冲突 | 双方的原文、投票、决定之后会怎样（V2-decision） |
| 维护空间里的列表 | 检查器 · 选中的领域 | 负责人、这周的工作、谁在读，去读它的链接（V2-space） |
| 管理后台里的列表 | 检查器 · 选中的连接 | 授权、用在哪里、到期以后会怎样（V2-sources） |
| 没有选中任何东西 | 不出现 | 中间占满宽度 |

修订从不直接改原始文档：文档在它的来源里，修订作为建议交给作者，改好后随下一次同步回来。

规则：

- **顶栏从不变化**，管理后台和账户里也一样。它从不切换空间。企业和个人知识库在账户菜单里切换。
- **左侧栏最多两级标题。** 文档树和知识树这样的树可以更深，但一次只展开一支。
- **界面自己的筛选和视图放在内容上方**，从不放在左侧栏。待办的种类是列表上方的一个菜单，数字卡片也能用来筛选。
- **阅读时左侧栏收起**，给正文留出宽度。正文上方的位置路径说明你在哪，跳转之后还说明你从哪来；它从不代替左侧栏。
- **紧凑是一种密度设置**（⌘.），不是一个地方。它从不改变导航里有什么。

### 按使用频率放置

最显眼的位置给人最常做的事。产品负责人看到企业切换器占着顶栏最显眼的位置时提出了这一点：大多数人只在一个企业里，很少切换。越常用，越靠近：每天用的放顶栏中间和左侧栏顶部，每周用的放左侧栏，每月用的放菜单或列表末尾，更少用的放设置，或只在 ⌘K 里。

| 东西 | 谁用 | 多久一次 | 放在哪里 |
| --- | --- | --- | --- |
| 搜索与提问 | 所有人 | 每天几次 | 顶栏正中，⌘K |
| 读知识页和文档 | 所有人 | 每天 | 中间，左侧栏收起 |
| 常用的空间 | 成员 | 每天到每周 | 左侧栏，常用的在前 |
| 待办 | 负责人每天；多数成员每月 0 到 2 件 | 每天到每月 | 左侧栏第二项，有事时带数字 |
| 维护一个空间 | 空间和主题的负责人（财务部的故事里 6 人） | 每天到每周 | 空间旁的“维护” |
| 我的空间 | 起草和发布的成员 | 每周 | 左侧栏 |
| 切换企业、打开个人知识库 | 多数人从不（只在一个企业）；少数人每周 | 很少 | 账户菜单最上面，以及 ⌘K“切换到…”。顶栏只用普通文字写当前企业名 |
| 全部空间 | 成员 | 每月 | 空间列表最后一行 |
| 管理后台 | 唯一的超级管理员 | 每周 | 账户菜单，只有超级管理员看得到 |
| 总是替我决定 | 负责人 | 设一次，偶尔看 | 在待办里一个决定下方的一行问话里开启；在账户里当前企业下面查看和暂停，待办里“已替你决定”那一行可以直接进去 |
| 紧凑模式 | 负责人 | 设一次 | 账户菜单里的开关，⌘. |
| 资料、语言、登录方式 | 所有人 | 每年几次 | 账户 |

每加一个新东西都过一遍同样的检查：谁用、多久用一次、它的位置配不配得上这个频率。

## 4. 两种节奏：阅读和处理

同一个结构服务两种很不一样的用法，变的只有密度：

- **阅读**是安静的。页面或文档占满中间，左侧栏收起，正文里只出现“已过时”和“有争议”两种标记。大多数成员只阅读。
- **处理**是密集的。负责人和超级管理员要清队列，所以紧凑模式用表格、快捷键和右侧检查器。队列仍然先给概述（第 7 节）。

### 储备：加粗关键短语

还没有排期。产品负责人 2026-11-04 提出：把一段话里承载要点的短语加粗，读者扫一眼就能抓住这一段想说什么。画布上的 V2-skim 画出了下面的建议。

- **在哪里。** 知识页、流程、卡片上的说明文字和回答，默认开。原文视图从不加粗，因为它显示的是作者写的样子；作者自己的加粗照原样显示。批注视图只加粗每段引文里的值。卡片上的值本来就醒目，不再加粗。
- **加粗什么。** 读者要找的那部分：事实的值（金额、上限、期限、日期）和改变它的条件（城市、职级）。一句话最多一个短语，从不加粗整句；一段加粗的字不超过约十分之一。
- **谁来挑。** 先从知识里来：一句话说的是哪条陈述，就加粗那条陈述的值和条件，所以每种语言加粗的是同一件事。其余由写这一页的那次模型调用一起标出，不另外调用模型。读者和负责人都不手动标。
- **和标记的关系。** “有争议”“已过时”的值不加粗，只留它的标记，免得把没定的值说得像定了。页面文字里的加粗只表示关键短语，不做别的用途，所以开关能干净地关掉它。加粗没有颜色，读屏软件也不会念出来，所以它从不独自承担意思。
- **读者的开关。** 页面“Aa”菜单里的“加粗关键短语”，默认开。它记在账户里，所以所有企业都一样；在“账户 › 资料与语言”和 ⌘K 里也能改。
- **三种语言。** 长度按字数算，因为中文和日文没有空格；短语从不切开一个词。只用加粗，不用斜体：中日文字体的斜体只是机器拉斜的。中日文的衬线字在 600 上和 400 几乎分不开，所以关键短语用 700。日文以后可以在语言包里换成着重号（傍点）；先用加粗，等日文读者看过再定。
- **成本和时机。** 约 1.5 到 2 人周，和知识页一起做，知识页还没建。PageSpec 的行内文字已经允许加粗，所以页面契约不变。批注视图需要一个附加字段：值在引文里的位置。写页面的提示词从第一版就带上这条规则，比以后再补便宜。用一次简短的阅读测试决定它是否默认开：有加粗和没有加粗时，找到答案各要多久。

## 5. 配置跟着负责的人走

| 谁负责 | 配置 | 放在哪里 |
| --- | --- | --- |
| 你本人，跨所有企业 | 名字、界面语言、登录方式、所在企业、通知 | 账户 › 你 |
| 你本人，在某个企业里 | 你的来源连接、使用知识的应用、助手可以替你决定什么、你的用量 | 账户 › 该企业 |
| 空间负责人 | 谁能读这个空间、领域和主题的负责人、文档的治理级别、审批和冲突设置（审批方式、截止日期、只由人决定的决定种类）、内容语言、规则 | 维护这个空间 |
| 超级管理员：企业 | 名称、默认语言、数据所在地区 | 管理 › 企业 |
| 超级管理员：人员 | 成员与席位、邀请、登录与加入（已认证的邮箱域名、企业自己的飞书组织、单点登录、通讯录同步） | 管理 › 人员 |
| 超级管理员：空间 | 空间、它们的负责人和读者、发布队列 | 管理 › 空间 |
| 超级管理员：来源与应用 | 企业的来源连接、企业智能体、成员可以授权哪些应用 | 管理 › 来源与应用 |
| 超级管理员：安全 | 敏感标签及哪些模型服务商可以处理它们、审计日志、为整个企业关闭“替我决定” | 管理 › 安全 |
| 超级管理员：用量 | 按成员和工作类型的用量、套餐、席位 | 管理 › 用量与账单 |

超级管理员决定“谁”和“怎么做”，从不决定知识说什么。所以主题负责人是空间负责人的配置，不是管理后台的页面。

## 6. 每个列表按真实规模来画

实测数字来自原型里 1 万份文档的模拟企业（见[规模化的陈述](statements-at-scale.md)）；其余是估计，要和设计伙伴核对。

| 列表 | 常见 | 大的时候 | 怎么显示 |
| --- | --- | --- | --- |
| 账户菜单里的企业 | 1 个，加上个人知识库 | 5 个 | 账户菜单最上面的一个普通列表 |
| 一个企业的空间 | 5 到 15 个 | 100 个以上 | 先列常用的空间，再是带搜索的“全部空间” |
| 一个空间的文档 | 300 到 3,000 份 | 5 万份 | 按来源应用和文件夹的树，按需展开，文件夹上带数量，可在里面搜索 |
| 一个空间的主题 | 10 到 40 个，分在 3 到 8 个领域 | 300 个 | 按领域折叠，带搜索。大小由聚类决定：约 100 条陈述时拆分 |
| 一个主题的陈述 | 约 1,000 条（实测中位数 1,143） | 6,000 条（实测最多 6,206） | 从不平铺。先列事实槽，再列用到它们的页面，其余按文档折叠，只显示数量 |
| 一个主题的页面、流程和卡片 | 5 到 15 个 | 50 个 | 列表 |
| 每位负责人每周的待办 | 2 条（p90 为 5），在一张卡片上 | 4 张卡片上 26 条；第一天 44 张专项卡片上 605 条 | 先给概述，再分成每张最多 20 条的卡片，每周最多 10 张 |
| 一个空间未解决的冲突 | 0 到 5 个 | 30 个 | 按截止日期排列 |
| 一个空间的发布申请 | 每周 0 到 3 个 | 20 个 | 按截止日期排列 |
| 一个企业的成员 | 10 到 200 人 | 5,000 人 | 先搜索，再筛选和批量操作；从不显示没有搜索的完整表格 |
| 一个空间的读者 | 用群组和人数表示，例如“采购部全体 18 人” | 数千人 | 显示群组，从不列出个人 |
| 一个空间的负责人 | 3 到 10 人 | 40 人 | 按领域排列，向下继承 |
| 来源连接 | 企业 2 到 8 个，每位成员 0 到 3 个 | 30 个 | 列表 |
| 每位成员使用知识的应用 | 1 到 5 个 | 20 个 | 列表 |
| 一个空间的规则 | 0 到 20 条 | 200 条 | 按种类排列，带搜索 |
| 每周替你决定的 | 0 到 40 项 | 300 项 | 一行合计，按种类分组，每组可撤销 |
| 一个页面的评论 | 0 到 10 条 | 100 条 | 按块分线程，已解决的折叠 |
| 搜索结果 | 10 条 | 每页 50 条 | 先给答案，再列结果 |
| 审计日志 | 每天数千条 | 数百万条 | 带筛选的查询，从不做成信息流 |

经验规则：10 条以内全部显示。10 到 100 条，按需要处理的程度分组或排序，其余折叠。超过 100 条，先搜索或筛选，显示概述和例外。没有上限的，是查询，不是列表。

## 7. 助手在界面里，安静地出现

Inspiration 是 AI 原生的产品，所以助手几乎出现在每个界面上。它应该像一个已经把材料读完的同事，而不是一个要人注意它的功能。

1. **每一堆事之前先给概述。** 待办箱、队列、批量变更、主题、搜索结果和导入的文件夹，打开时都先有一段概述，根据引擎的数字写成：发生了什么、哪些需要你、哪些它可以处理。数字从不在句子里罗列。要紧的几个数字，最多四个，放在一行卡片上：每张写数值、一句简短的趋势（“上周 4 件”“比上月多 18”），趋势要紧时再加一条小折线；卡片也是筛选。卡片下面两三句话只说这些数字意味着什么，讲性质或趋势，不复述数字：“这周比平时多一些，多数是例行的复核和备注，可以按你平时的决定处理。需要你的是一个票数持平的会签、一次权限收紧和一个审批权限的冲突。”数字只在操作的名字里出现，比如“按建议处理这 6 件”。
2. **建议就是默认值。** 需要人来选的地方，助手的选择已经预先选好，标着“建议”，附一句理由。按回车就是确认；选别的只要点一下。没有聊天气泡，也没有“AI 认为”面板：建议体现在控件的状态里，也就是选中了哪项、什么排在前面、什么被折叠。
3. **“替我决定”放在成堆的事上。** 在概述或卡片上，一个操作就把助手可以决定的都处理掉，其余标为“留给你”。单个条目通过接受建议来决定，所以不会在每一项上都放一个“替我决定”按钮。任何地方都可以用 `d` 键和 ⌘K 调出它。某人连续五次接受同一类决定的建议后，助手会在这个决定下方用一行字问一次，要不要以后这类都替他决定。
4. **“留给你”，并说明原因。** 助手不能或不该决定时（人与人意见不同、会改变谁能读、无法撤销、没有把握，或空间把这类决定留给人），用一行字说明原因，并照样填好它的建议。
5. **展示结果，不展示过程。** 助手的工作以结果出现：一个预先选好的选项、一个排好序的列表、一张写着“本周已替你决定 34 件，撤销了 2 件”的卡片。它不播报进度，也不弹出没人要的窗口。
6. **助手做过的每件事都有“为什么”和“撤销”。** “为什么”显示理由和它读过的段落；“撤销”恢复之前的状态，把这一项交还给人。
7. **没有自己的样式。** 助手没有头像、闪光图标或专属颜色。它的标记是文字（建议、已替你决定、留给你），小而低调，从不比人自己的内容更显眼。
8. **提问随时可用，但从不挡路。** 首页的提问栏、处处可用的 ⌘K，以及选中任何文字后的“就此提问”。答案就地出现在面板或浮层里，带引用。

刻意不做的：每个界面上的聊天侧栏、每一项上的 AI 按钮、AI 徽标、不留记录就生效的改动，以及没人问起的概括。委托的具体规则见[替我决定](decide-for-me.md)。

## 8. 这对画布意味着什么

按本文检查设计画布（第 72 版）的结果：

| 画布上发现的问题 | 依据 | 下一版 |
| --- | --- | --- |
| 六种不同的顶栏：账户和管理界面去掉了切换器或搜索，有些把“紧凑”画得像一个地方 | 第 3 节 | 每个界面同一个顶栏；紧凑是一项设置 |
| 九种左侧栏：区域菜单、待办筛选、维护工具、管理列表、账户列表、文档树、追溯大纲，或者没有 | 第 3 节 | 左侧栏总是四个区域之一；筛选和大纲移进界面内容 |
| 管理后台是一个平铺列表，混着人员、空间、来源和安全，还放着本属于空间负责人的“主题负责人” | 第 5 节 | 管理后台按关注点分组；主题负责人放在空间里 |
| 真实有几百条的列表（成员、主题、空间）只画了三到五行，也没有搜索 | 第 6 节 | 每个列表按常见规模画，并说明变大以后的样子 |
| 助手有六种出现方式：“建议”标签、“系统建议”、评论回复、普通文字、完全不出现，以及每一项上的“替我决定”草稿按钮 | 第 7 节 | 统一一种模式：概述、建议即默认值、“替我决定”放在成堆的事上 |
| 两个演示故事，人物也不同：英文画的是采购，中文画的是财务差旅 | | 所有界面用同一个故事、同一组人物 |
| 画布上用“负责人”，文档里用“维护人” | 产品负责人于 2026-11-05 决定沿用“负责人” | 一律用“负责人”；第二版画板在重画之前仍写“维护人” |
| 早期探索 A、B、C 和选定的设计放在同一张画布上 | | 移到归档区 |

第二版（画布第 74 版，[界面稿](screens/README.md)中的 V2 两行）把这些规则用在十九个界面上。第一行是结构、阅读、账户和管理后台；第二行是处理工作：待办、决定、维护空间、发布和追溯。第一版里只有导入后的三块（E-doc、E-doc-layers、E-doc-knowledge）仍然有效。画布第 79 版把第 3 节的放置表用到第二版所有画板上：顶栏用普通文字写企业名，企业在账户菜单里切换；“替我决定”不再是账户菜单里的一项，因为它发生在待办和每个决定里，它的设置是账户里的“长期委托”。这一版还加了 V2-tree，比较了空间的文档和知识在左侧栏里怎么放的四个备选；产品负责人选择保留今天的样子，文档和知识放在每个空间下面。

画布第 80 版把产品负责人接下来的三条评论用到第二版所有画板上。四个区域靠左侧栏分开（纸面、带靛蓝区域头的淡蓝底、深色、账户的标题），阅读以外的每个界面都以从区域开始的位置路径开头，跳转之后多一个回去的路。右侧栏永远有标题，并跟着选中的东西走：新加的 V2-doc 是阅读原始文档，旁边是评论和提一个修订；V2-page 是知识页，旁边是这一页正在处理的事。概述把数字移到最多四张带趋势的卡片上，句子只说这些数字意味着什么（首页、待办、维护空间、批量变更、文档、成员和来源连接）。

画布第 81 版把产品负责人觉得看不懂的“长期委托”改名为**总是替我决定**，和人已经熟悉的那个操作同名：“替我决定”是这一次，“总是替我决定”是以后都这样。每一类写成两栏的规则：“当这件事出现”和“助手就这样处理”；这一页还画出一类事是从哪里来的：待办里一个决定下方的一行问话。在[替我决定](decide-for-me.md)的规格里，它仍叫“长期委托”。

画布第 86 版加了 V2-skim，画出第 4 节放在储备里的“加粗关键短语”。

## 9. 界面需要引擎提供什么

2026-10-27 对照引擎检查（`main` 合入拉取请求 #24 之后，以及引擎线程正在做的验证）：

- **概述。** 协作组件已经按负责人、主题、事实槽和周给待办分组。概述还需要每个人的一次汇总读取：按种类和原因的数量，以及哪些可以由助手处理。这是新增。
- **建议即默认值。** 治理组件已经会提出最权威的现行值并给出理由（GV-1），待办也已经带一键处理选项（`TodoResolution`）。处理选项需要标明哪一个是建议的、为什么。这是新增。
- **替我决定。** 委托的契约和对 AG-4 的修改见[替我决定](decide-for-me.md)，动手前需要先达成一致。
- **留给你。** 待办需要记录它为什么留给人。这是新增。
- **撤销。** 决定都有记录（GV-7），知识从不删除，所以撤销是一个恢复旧状态的新决定。
- **加粗关键短语（储备，见第 4 节）。** 页面合成建好以后，用加粗标出关键短语，加粗不做别的用途。批注视图需要每段引文多一个附加字段：陈述的值在引文里的位置。
- **引擎怎么判断，就用文字说出来。** 引擎现在把没有日期的文档按最后修改时间排先后，并让原文优先于它的译文。“这段讲了什么”和文档树会用文字说明，比如“比……新”“……的译文”。
