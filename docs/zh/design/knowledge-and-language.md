# 知识与语言

状态：已采纳的原则，2026-10-26，来自产品负责人在总览上的评论：知识是知识，语言只是知识的一种表现形式；这一点贯穿整个系统设计。除各节注明的部分外，均已设计、尚未实现。本文是 [docs/design/knowledge-and-language.md](../../design/knowledge-and-language.md) 的中文副本，两者不一致时以英文版为准。

## 原则

每一个知识单元都有不依赖语言的身份：一条陈述、一个事实槽及其值、一个实体、一个主题、一个流程、一个页面。语言属于这些知识的表达：来源的原文、标签、页面的行文、回答。由此有四条规则。

1. **一个单元，多种表达。** 同一份知识用两种语言写，是一个单元的两种表达，永远不是两个单元。不会因为写了两遍就重复。
2. **比较的是意思，不是措辞。** 两种语言不会因为措辞不同而冲突。冲突是关于意思的，例如同一个事实有两个值。落后于原文的译本是过时的副本，不是第二种意见。
3. **证据保持原来的语言。** 引文始终是来源语言的原文，“引文必须是其段落的原样子串”这条规则不变。展示给读者的翻译标明是机器翻译，一键可回到原文。人写的内容从不被悄悄翻译。
4. **每个人读自己的语言。** 一个人读到的内容，用这个人自己的语言从同一份知识生成，并说明哪些是机器写的。

## 语言在哪里

| 单元 | 与语言无关的部分 | 某种语言的表达 |
| --- | --- | --- |
| 来源版本 | 它的身份，带稳定 ID 的块和片段，以及作为事实记录下来的文档语言和每个块的语言 | 原文本身，逐字保留 |
| 陈述 | 它的意思：类型、主语实体、谓词、限定条件、带类型的值、生效时间 | 表达它的每条抽取出的陈述的文字；证据引文保持来源语言 |
| 事实槽 | 它的键：主语实体 ID、谓词键、限定条件键。值带类型并规范化（“600 元”和“CNY 600”都是每晚 600 CNY） | 谓词和限定条件的英文、中文、日文标签，以及在文档里识别它们的别名 |
| 实体 | ID、类型和外部键（统一社会信用代码、工号、SKU） | 各语言、各文字体系的名称和别名（北京、Beijing） |
| 主题 | 它的键和在知识树里的位置 | 各语言的标题和摘要 |
| 页面和流程 | 它们的结构：绑定到陈述的章节和步骤 | 各语言的行文。空间的内容语言是标准版本 |
| 回答 | 它用到的陈述和段落 | 提问者的语言；引文保持原文 |
| 待办、备注、事件 | 代码和参数 | 每位接收者的语言（业务层已按此设计） |

已经实现的：来源版本和陈述的语言是记录下来的字段，谓词键与语言无关，值带类型并已规范化。来源给出的译本（在文件夹中，"leave-policy.zh.md" 位于 "leave-policy.md" 旁边）与原文关联，治理把两者算作一个来源（[对照语料](../../../examples/control/README.zh.md)，translated-policy）。译本给出的值与原文不同时，无需人工即以原文为准；原文被编辑后，它的译本会收到复核，直到重新翻译（[Kubernetes 页面](../../../examples/kubernetes-docs/README.zh.md)，英文、中文和日文）。尚未实现的：限定条件键（演示目录用中文词作键）、中文以外的各语言别名、实体解析，以及下文的全部内容。

## 贯穿整条流水线

- **规范化**记录每篇文档和每个块的语言，并建立译本关系。一篇文档是另一篇的译本，要么来源自己这么说（飞书、Confluence 或 Notion 的语言版本），要么对齐结果表明如此：结构相同、数字和日期相同、逐块的多语言向量相似。来源给出的关系记为 `DocumentMetadata.translation_of`（文件夹来源已实现）；引擎识别的关系由规范化自己记录，因为版本一经写入就不可更改。
- **抽取**用与语言无关的形式填写陈述的意思：来自目录的谓词键和限定条件键、实体解析后的实体 ID、带类型的值。陈述文字保持来源语言，提示词说明这种语言。
- **陈述跨语言合并。** 候选来自多语言向量和共享同一个事实槽。只有模型确认意思相同（包括条件）时才合并，从不只凭相似度合并。合并后的陈述保留每条原陈述的证据，每段引文都是各自语言的原文。这就是治理已经计划的“把陈述合并为规范陈述”，扩展到跨语言。
- **实体解析跨语言、跨文字体系：** 先用外部键，再用各语言的名称和别名、音译和目录里的列表，最后由模型确认。
- **治理比较意思。** 支持按独立来源计数，译本和原文算作一个来源，从不算第二个来源（来源给出的关系已实现）。一篇文档和它自己的译本说法不同，不是来源之间的冲突：以原文为准，译本收到一条“译本已过时”复核，挂在原文的这次变更上，和现在编辑后落下的副本收到复核一样（来源给出的关系已实现）。两篇用不同语言独立写成的文档给出不同的值，是真冲突；审阅人看到每个值各自语言的引文，以及标明的翻译。
- **保鲜**在原文变更时，给译本发出副本现在已经会收到的复核（副本和来源给出的译本已实现）。
- **主题**用多语言向量聚类，所以一个主题会收齐各种语言的陈述。主题的标题和摘要按语言分别撰写。
- **页面编译器**只构建一次页面结构，按语言生成行文。标准版本使用空间的内容语言。读者可以要求用自己的语言阅读一个页面：它会用该语言从同一批陈述编译出来，而不是翻译页面的文字，并标明由机器撰写。引文保持原文语言。一个人的编辑用一种语言写成；其他语言的版本以标明的翻译带上它。
- **检索**使用多语言向量和按语言划分的全文索引（已设计）。在几种语言里都找到的同一条陈述只返回一条结果，并列出它的其他语言。
- **界面**每个知识单元只显示一项。追溯视图列出各种语言的证据，读者看到自己的语言，一键可回到原文。

## 验收测试

下面这些用例在内存替身和真实服务栈上都通过，工作才算完成，并配一个多语言评测语料（英文、中文、日文），包含译本、独立文档和真正的分歧：

| 用例 | 预期 |
| --- | --- |
| 一份中文制度和它的英文译本给出同一个限额 | 事实槽只有一个值。支持计为一份文档及其译本，而不是两份。没有冲突 |
| 中文原文把 600 改成 650，英文译本没改 | 650 生效。译本收到一条“译本已过时”复核，挂在原文的这次变更上。不给主题负责人发冲突待办 |
| 独立写成的日文文档和中文文档给出不同的限额 | 一个冲突，每个值附各自语言的引文，并给审阅人标明的翻译 |
| 同一个流程步骤在中文和英文里都以没有事实槽的普通陈述出现 | 一条陈述，带两份证据；搜索只返回一条结果 |
| 两种语言的两条陈述看起来很像，但条件不同 | 不合并：模型确认不通过 |
| 一位中文读者要求用中文阅读一个英文空间的页面 | 页面用中文从同一批陈述编译出来，标明由机器撰写；引文保持英文 |

对来源给出的译本，前两个用例现在已在对照语料和 Kubernetes 语料中通过。

## 契约变化

都是新增，流程见 [docs/contracts.md](../../contracts.md)。

- `DocumentMetadata` 新增可选的 `translation_of?: SourceRef`，即来源给出的原文文档，随其余元数据一起进入版本（已实现）。识别出的关系由规范化保存，并注明识别方式，而不是像本节最初提议的那样，作为 `translation_basis` 放在不可更改的 `SourceVersion` 上。
- `Claim` 新增可选的 `expressions[] { language, statement, claim_ids }`，用于跨语言合并后的规范陈述。每条成员陈述保留自己的 `language`、文字和证据。
- `Entity` 新增可选的 `names[] { language, name, aliases }`；`name` 仍是默认显示名称。
- `TaxonomyNode` 新增可选的 `titles { <locale>: string }`；`title` 仍是标准标题。
- `PageSpec.locale` 表示一个版本的语言；其他语言的版本新增 `rendering_of?: PageId`，指向标准页面。
- 谓词目录（配置，还不是契约）给每个谓词和限定条件一个与语言无关的键，以及英文、中文、日文的标签和别名。

## 引擎工作量

总览里的国际化工作已经包括语言识别、各语言别名和与语言无关的事实槽键。本文在此之上增加：

| 组件 | 变化 | 人周 |
| --- | --- | --- |
| normalization | 译本关系，来自来源或通过对齐识别 | 0.5 |
| extraction、governance | 带模型确认的跨语言合并；译本和原文算一份；用“译本已过时”代替冲突 | 1 |
| 实体解析 | 各语言、各文字体系的名称，作为实体解析的一部分 | 0.5 |
| page-compiler | 从陈述用另一种语言生成页面 | 1 |
| 契约、测试和评测 | 上述变化、验收用例和多语言语料 | 0.5 |
