# 来源变化：删除与大规模变化

状态：已采纳的设计，2026-10-26，来自产品负责人在总览上的评论。除非某一节另有说明，都还没有实现。阈值和时限是默认值，原型实测后可以调整。本文是英文版 [docs/design/source-changes.md](../../design/source-changes.md) 的中文副本，两者不一致时以英文版为准。

## 摘要

来源一直在变：某个值被更正，制度出了新版本，文档被删除，文件夹被整理，应用失去了某个知识库空间的访问权。四条规则决定引擎怎么做、什么时候需要问人：

1. **进入系统的知识从不被静默删除。** 每一次移除，要么由人决定，要么作为一个看得见、可撤销的默认处理记录下来。
2. **来源自己更正时静默同步。** 只有多个来源彼此说法不同才需要人，而且这个人能看到各有多少来源支持哪种说法。
3. **来源文档被删除时保留它的知识，** 标记“原文已删除”，并问它的维护人一次：保留为快照、指向替代文档，还是不保留。
4. **大规模变化作为一次变化来审阅，** 绝不变成一大批待办。

## 各层之间的关系

引擎有三层。只有第一层跟随来源，而且只单向跟随。

| 层 | 存什么 | 谁来改 | 来源变化时 |
| --- | --- | --- | --- |
| 来源版本 | 每篇外部文档每个版本的不可变副本，按带稳定锚点的块存放（飞书 block ID，文件的页码和段落），文档消失时记一个删除标记 | 只有来源同步，从来源单向写入 | 追加一个新版本，之前的版本都保留 |
| 知识 | 带原文证据的陈述、事实槽、主题、页面和流程 | 只有流水线，从来源版本和人的决定推导 | 只重读变化的块。陈述被关闭（被取代或撤回），从不删除 |
| 人的工作 | 评论、更正（override）、决定、裁决规则、人工新增的陈述 | 人 | 重新挂到锚点上。来源已经追上的更正自动退役；来源与之矛盾的更正给作者一条待办；锚点找不到的评论标为“孤立”，显示在页面旁边，从不丢弃 |

系统从不写回来源。不管人的工作离来源多远，系统里的来源副本始终等于来源本身，所有差异都在人的工作里，每一处都有作者和日期。所以每次同步都是同样三步：追加新版本，在块变化的地方重新推导知识，把人的工作重新挂到锚点上。

已实现：来源版本、块锚点和知识层。评论、更正和重新挂锚只有契约（`Anchor`、`Override`、`CommentStatus.orphaned`、`TodoKind.override_conflict`），还没有实现。

## 同一来源内的变化

一个来源改了自己的值（A 变成 B），引擎把它当作来源自己的修正。新陈述在同一个事实槽里取代旧陈述，槽里只有一个值，不问任何人。追溯视图保留两者，以及各自成立的日期。这已经实现：抽取用新陈述取代被关闭的陈述，事实槽只有一个值时治理什么都不问。

新版本不再写某个事实、也没有给出别的值时（删掉了一段，或者页面被替换成“This page has moved”通知），这个事实继续有效，标记为“来源中已不再写明”，文档的维护人收到这篇文档的一条待办，列出它不再写明的所有内容：保留或不保留。之后的版本重新写明这个事实，标记就去掉；给出别的值，就按上面的方式取代它；待办随清单更新，清单为空时撤回。不写事实、被某个版本改写或删掉的行文会被关闭，页面跟随文档。已实现：标记（`Claim.unstated`）、待办（`TodoKind.unstated`）、恢复和取代；选择保留或不保留之后做什么，还没有实现。[examples/gitlab-expenses](../../../examples/gitlab-expenses/README.zh.md) 用一份真实制度六年间的这类变化做了回放。

唯一的例外是人在这个值上做过的工作。如果有人更正过它，或裁决过关于它的冲突，这个人会收到一条待办：保留自己的更正，还是跟随来源。

## 来源之间的分歧

两个或更多当前有效的来源对同一个事实槽说法不同，和现在一样，是需要人来处理的冲突。冲突待办现在还会显示每个值的支持情况：

> 9 份文档说 500（1 份制度、8 份会议纪要）；1 份文档说 600（价目表）。

支持按不同的文档计数。一篇文档的副本只算一份，用的是规范化已有的完全重复和近似重复检测。每个值都显示其文档的权威和治理级别。数量只是参考：建议值仍然按权威和日期决定，因为一份受治理的制度应当压过九份会议纪要。

## 来源文档被删除时

### 引擎现在怎么做

来源同步发现删除（Webhook、每 15 分钟一次的轮询或每晚的全量对账），写入一个删除标记版本；之前的版本留在历史里。规范化把文档标为已删除，它的段落退出搜索。抽取让只以这篇文档为证据的陈述继续有效，加上标记（带 `deleted` 的 `Claim.unstated`），并给文档的维护人一条 `source_deleted` 待办，列出这些陈述；文档恢复后，标记去掉，待办撤回。保鲜忘掉这篇文档的复核时钟。

还缺的是下面设计的其余部分：失去访问权限的检查、移动、各项选择及其记录，以及 30 天后的默认处理。

### 设计

1. **先确认是删除。** 一次同步发现某个来源超过 10% 的文档、或超过 50 篇文档同时消失，更可能是失去了访问权（应用被移出了知识库空间、令牌过期），而不是删除。这时来源同步不写删除标记，暂停该来源，给超级管理员一条连接待办。修好连接就等于什么都没发生；确认确实删除了，就作为一个变更批次处理（见下文）。来源的接口能区分“已删除”和“无权访问”时，原因记在版本上。
2. **识别移动，但只在同一个权限边界内。** 一篇文档消失的同时，24 小时内同一企业某个已连接的来源里出现了文字相同或几乎相同的文档，就是一个移动候选。文字相同只说明两者是同一篇文档，从不决定谁能看到挂在它上面的工作。只有新位置在同一个域里、新空间的每位读者原本就能读旧空间、且新的敏感标签不更低时，移动才静默完成（知识、人的工作和决定跟着它走，追溯里记下这次移动，不问任何人）。否则新文档按一篇新文档开始，不带旧的评论、更正和决定，旧文档走下面的步骤；它的待办提供“把人的工作迁过去”，这是一次按现有规则的发布申请（见[业务层与引擎契约](business-engine-contract.md)）：由新空间的维护人、以及这次移动扩大了受众的每个空间的维护人审批。在“我的空间”和共享空间之间，永远是发布，不是移动。
3. **在有人决定之前全部保留。** 陈述继续有效，证据仍能打开最后一个版本。引用和追溯视图显示“原文已于 10 月 20 日删除”。页面正文仍只有“已过时”和“有争议”两种标记。企业策略也可以改为在决定之前隐藏这类知识（`source_deleted: keep | hide`，默认 keep），适合删除往往意味着文档被撤回的企业。
4. **只问失去全部支撑的内容。** 来龙去脉能说明哪些陈述在别处还有证据：这些静默重新决定。只有唯一证据就是被删文档的陈述，以及引用它们的页面和流程，才进入待办。没有这样的陈述，就没有待办。
5. **每篇被删文档或文件夹、每位维护人一条待办。** 待办发给每个受影响主题的维护人，列出涉及的主题、页面、流程和陈述。删除一个有 30 篇文档的文件夹，每位维护人收到一条待办，而不是 30 条。维护人可以一次为全部内容选择，也可以逐项选择：

| 选择 | 结果 |
| --- | --- |
| 保留为快照（默认） | 最后一个版本变成快照来源：冻结、没有连接，带一个复核日期（默认取其陈述所属类别中最短的复核周期）。陈述继续有效并引用快照。评论、更正和决定仍挂在它上面。引用显示“原文已删除，已保留快照” |
| 指向替代文档 | 维护人选一篇文档，引擎推荐最相似的几篇。按移动处理：新文档支持的陈述连同人的工作一起迁过去，其余的列给维护人。第 2 步的权限检查同样适用：受众更广、或在另一个域里的替代文档，只能通过发布申请把人的工作迁过去 |
| 不保留 | 只以这篇文档为证据的陈述被撤回：关闭，仍在追溯里。引用它们的页面和流程重建，治理重新决定它们的事实槽 |

6. **每个选择都是一条记录：** 谁决定的、何时、选了什么、保留了哪个版本，以及可选的理由。它显示在追溯视图和“为什么是这个值？”里，以后任何人都能看到知识为什么还在、或为什么没了。
7. **没有什么会永远悬着。** 30 天没有决定，就保留为快照并记为“默认保留”，带复核日期。默认保留只决定存储，从不决定可见性：快照留在原来的空间，沿用该空间的受众和最后的敏感标签；待办期间被隐藏的知识（`source_deleted: hide`，或契约中的 `source_restricted: quarantine`）继续隐藏，在追溯里显示为“默认保留，已隐藏”。重新显示是一个单独的决定，和其他决定一样留记录：`hide` 由主题维护人决定，`quarantine` 由空间维护人决定。决定之前文档在来源里恢复了，待办撤回，什么都没变。选了“保留”之后文档恢复，回到正常同步，历史接着往下记。选了“不保留”之后文档恢复，恢复的陈述作为新的出现回来，照常治理。

按治理级别：

| 级别 | 决定之前 | 通知谁 |
| --- | --- | --- |
| 严格 | 保留并标记 | 给受影响主题的维护人一条待办 |
| 宽松 | 保留并标记 | 在空间维护人每周的通知卡片上出一条通知，可一步“不保留” |
| 仅检索 | 段落留在搜索里，并标记 | 不通知 |

在“我的空间”里，成员自己就是一切的维护人，这些待办由成员本人处理。

## 大规模变化：一个原因，一次审阅

有些事件一次就涉及几百条陈述：制度从第 3 版改到第 4 版、知识库空间整体整理、整个文件夹的治理级别被调整、某个连接失去访问权。把它们拆成普通待办，即使有每周上限，也会淹没维护人的待办箱。所以待办箱按原因来归并工作。

- **每个待办请求都带着它的原因。** 原因就是事件的 `correlation_id`：一个来源的一次同步、一次文件夹删除或移动、一篇文档的一个新版本、一次治理级别调整、一次重建。协作现在已经用它把副本复核放到引起它的冲突卡片上。
- **大的原因变成变更批次。** 一个原因产生的待办超过一张卡片（20 条），或涉及 3 个以上主题时，这些待办作为一个变更批次放在一起，不进每周卡片。
- **交给覆盖范围最小的维护人：** 一个主题内交给主题维护人，一个空间内交给空间维护人，跨空间的变化交给超级管理员指定的一位维护人，连接问题交给超级管理员。
- **审阅先说发生了什么。** 例如：“财务空间的《费用制度》从第 3 版更新到第 4 版：41 个值变化，6 个与其他来源不一致，3 篇文档被删除。”然后是按类型和主题的数量、样例，以及每个争议值的支持情况。
- **决定可以整体做。** 全部跟随来源、全部保留、按主题逐个看，或把某些主题交给各自的维护人，这些部分就变回普通卡片。每一项仍有自己的决定记录，指向这次批次决定，追溯不会丢掉任何一项。
- **审阅期间读者看到的和单条待办时一样：** 上一次核实过的值标为“有争议”，被删的来源保留并标记。

原因分三类，处理方式不同：

| 类别 | 例子 | 怎么处理 |
| --- | --- | --- |
| 系统 | 应用被移出知识库空间、令牌过期、大量文档同时消失 | 不是知识变化。来源同步在写入任何东西之前停下（上文第 1 步的检查），暂停该来源，给超级管理员一条连接待办。连接修好，就当什么都没发生；文档确实被删了，就作为一个变更批次 |
| 引擎 | 提示词或模型升级、重新抽取、主题重新聚类 | 值不变就必须静默：重新抽取得到同样的陈述，现在就什么都不问。大量值变化说明是质量回归：这次运行先交给工程团队评测，永远不进任何人的待办箱 |
| 内容 | 制度改写、文件夹整理、一篇文档拆成几篇 | 变更批次审阅 |

新企业第一天的首次复核专项（已实现）就是这条规则的第一个例子：它的原因是来源的首次连接。

## 验收测试

下面这些用例在内存替身和真实服务栈上都通过，引擎工作才算完成：

| 用例 | 预期 |
| --- | --- |
| 文档在同一个空间内改名或移动 | 引用、评论、更正和决定跟着它走；追溯记下这次移动；不问任何人 |
| 文档从“我的空间”消失，共享空间里出现了相同文字 | 不算移动。共享空间的副本是一篇新文档，不带成员的评论、更正和决定。成员收到“我的空间”那篇文档的删除待办，其中一个选项是发布自己的工作 |
| 文档从受限空间移到受众更广的空间 | 新空间里按文字重新构建知识。人的工作留在旧空间的快照上，除非发布申请获批，更广的受众永远看不到 |
| 启用了 `source_deleted: hide` 或 `source_restricted: quarantine`，30 天没有决定 | 快照保留并继续隐藏，记为“默认保留，已隐藏”。只有主题维护人（`hide`）或空间维护人（`quarantine`）能让它重新显示 |

## 契约变化

都是新增，流程见 [docs/contracts.md](../../contracts.md)。

- `TodoKind` 新增 `source_deleted`（已实现）、`unstated`（已实现：新版本不再写明的事实）和 `change_set`。
- `Claim` 新增 `unstated { since, source_version_id, deleted? }`（已实现）。
- 新增 `ChangeSet { id, tenant_id, cause { kind: sync | folder_deleted | folder_moved | connection_lost | new_version | level_changed | first_connection | rebuild, source_id?, correlation_id }, counts { by_kind, by_topic }, todo_ids, assignee_id, status: open | decided | split, decision_id? }`。
- `SourceVersion` 新增可选的 `deletion_reason: deleted | no_access | moved` 和 `moved_to?: SourceRef`；只有通过权限检查的移动才记为 `moved`。
- `source_deleted` 的决定方案：`keep_snapshot`、`replace`（带一个 `SourceRef`）和 `retire`。没通过权限检查的 `replace` 会发起一次发布申请，而不是直接迁移人的工作。
- `TenantPolicy` 新增 `sources { source_deleted: keep | hide }`。
- `ConflictCase` 新增 `support[] { value_key, documents, by_authority }`。
